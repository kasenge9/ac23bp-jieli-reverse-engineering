# Reverse Engineering and Functional Analysis of a JieLi AC23BP Bluetooth Audio MP3 Module

## Abstract

This document presents a research white paper focused on the reverse engineering and functional analysis of a small Bluetooth MP3 speaker module built around a Jieli (JieLi) audio System-on-Chip (SoC), identified on the board as `AC23BP 1K966-65E4`. The project investigates the hardware design, radio behavior, audio subsystem, power architecture, and firmware characteristics of the module while preserving a disciplined, evidence-based approach. The objective is not merely to modify the device name or rebrand the unit, but to understand the module as an embedded Bluetooth audio platform from the physical board level down to firmware and functionality.

The investigation begins with the observed Bluetooth identity `CHARGE MINI` and the discovered Bluetooth MAC address `93:91:63:79:F6:A9`, coupled with a Windows registry observation showing a cached name that differs from the actual broadcast name. This finding is a key insight: the device’s real Bluetooth identity is generated by the module itself and is therefore expected to be controlled by onboard firmware or configuration data rather than by the host operating system. This motivates a deeper reverse-engineering effort into the physical hardware and firmware storage model.

The silicon is provisionally identified as belonging to the Jieli AC6965E family, a Bluetooth audio SoC used in speaker and multimedia applications. The board includes a 24.000 MHz crystal, PCB antenna, USB-A flash-drive interface, microSD/TF slot, power input, and audio signal routing to an amplifier and speaker section. The project is intentionally structured around a strict investigation sequence: (1) identify the SoC and hardware architecture, (2) map power and interfaces, (3) identify debug or programming pads, (4) inspect firmware storage and configuration, and (5) analyze how the module exposes Bluetooth and audio behavior.

The eventual outcome is a documented understanding of the device as a complete embedded platform, including PCB-level mapping, pin-level analysis, power subsystem, radio section, audio path, firmware structure, and external interfaces. This paper is intended to serve as an engineering note and foundational white paper for further investigation, reproduction, or controlled experimentation.

## 1. Introduction

This project began with a low-cost Bluetooth MP3 speaker module recovered from a compact robot or speaker unit. The board contained a main IC bearing the marking:

```
AC23BP 1K966-65E4
```

The module also included a 24 MHz crystal, RF-related circuitry, a PCB antenna, USB-A port, microSD slot, auxiliary/interface pads, and power wiring. The initial practical observation was that the speaker presented itself to Windows as a generic device named `CHARGE MINI`, with the Bluetooth MAC address `93:91:63:79:F6:A9`.

The original user goal was not simply to make the device advertise a different name. Instead, the objective was to understand the system at a deeper level: how the module works, what control surfaces it exposes, what hardware is present, and how firmware defines its identity and operations.

The investigation produced a key realization: the Windows-side cached device name was not authoritative. The actual broadcast name came from the device firmware. This finding established the central technical direction of the project: the module’s true identity and behavior are hosted inside the device itself, not merely in the host computer or the OS driver stack.

The project therefore addresses a broader question: what is the actual architecture of this Jieli-based Bluetooth audio module, and how can it be reverse engineered in a systematic and non-destructive way?

## 2. Background and Observations

### 2.1 Device Class

The module is a small Bluetooth speaker/MP3 audio board designed to provide:

- Bluetooth audio streaming
- local media playback from USB flash drive
- local media playback from microSD/TF card
- optional AUX/audio input paths
- onboard audio amplification and speaker drive
- simple control interfaces for playback and power

The device is not merely a Bluetooth radio attached to a speaker amplifier; it is an integrated embedded system combining radio, digital audio processing, storage support, and user-interface logic.

### 2.2 Initial Windows Observations

From a Windows laptop, the device appeared as:

- Name: `CHARGE MINI`
- Bluetooth address: `93:91:63:79:F6:A9`
- Generic Microsoft Bluetooth peripheral classification

The Windows registry contained a cached device entry under:

```
HKLM:\SYSTEM\CurrentControlSet\Services\BTHPORT\Parameters\Devices\93916379F6A9
```

This registry path stored the cached device name. It was discovered that changing the Windows-side value changed only the local cached record and not the actual device broadcast name. This led to the conclusion that the host machine was not controlling the module’s identity; instead, the module itself advertised its own configured name through its firmware.

### 2.3 Significance of the Discovery

This was a critical turning point in the project. It showed that:

- the host OS does not define the true module branding,
- the module firmware stores or generates the advertised name,
- the design is likely using a firmware-defined Bluetooth configuration,
- and the highly relevant path forward is to investigating the SoC, memory, and board-level interfaces rather than only the host side.

This insight reframes the effort from a simple naming challenge into a full integrated reverse-engineering project.

## 3. Device Identification and Working Hypothesis

### 3.1 Marking Interpretation

The main IC is marked:

```
AC23BP 1K966-65E4
```

The working hypothesis is that this corresponds to a Jieli (JieLi) Bluetooth audio SoC in the `AC6965E` family.

The reasoning follows a plausible but non-definitive interpretation:

- `AC23BP` / `1K966` appear to be manufacturing or laser-marking identifiers,
- `65E` is associated with the `AC6965E` silicon family,
- `4` is interpreted as indicating a 4 Mbit flash configuration or nearby package/variant coding,

The precise conversion from the laser-marked code to an official silicon part number is not publicly documented in the available material, so the identification remains a working hypothesis rather than a final proven fact.

### 3.2 Reference Silicon

A datasheet for the Jieli `AC6965E` was obtained and studied. The part is described as a Bluetooth audio SoC suitable for speaker and multimedia devices, and it includes:

- Bluetooth 5.1
- BR/EDR
- BLE
- DSP and audio processing
- USB 2.0 OTG support
- UART, I2C, ADC, GPIO
- power management
- RF interface logic
- speaker/audio application targeting

This makes the AC6965E a plausible reference for the target board. However, the exact physical pin mapping of the observed module is not yet proven to match the datasheet exactly without board-level validation.

## 6. Research Methodology

The reverse-engineering methodology is intentionally conservative and evidence-based.

### 6.1 Non-Invasive Observation

The first stage consists of:

- board photography
- front and back board inspection
- close-up imaging of IC, crystal, RF path, and connectors
- documenting visible traces and component grouping

### 6.2 Continuity and Electrical Mapping

The next stage involves:

- continuity testing between major components
- identifying power rails and ground domains
- tracing the UART and USB pins if available
- identifying the crystal oscillator network
- mapping audio lines to amplifier and speaker interfaces

### 6.3 Controlled Safety

Because the board contains unknown interfaces and a potentially powered or battery-backed design, the process must avoid direct connection to arbitrary test pads without first determining their function. This safety-first approach is essential to prevent accidental damage to the SoC or attached peripherals.

### 6.4 Firmware-First Investigation Strategy

Once hardware access is understood, the next goal is not to modify the device but to observe and document:

- how the system boots,
- how it stores configuration,
- how it publishes its Bluetooth name,
- and how audio and media functions are implemented.

This preserves the scientific goal of reverse engineering rather than the immediate objective of altering the product name.

## 8. The Key Windows Discovery and Its Implications

The most important initial experiment was the Windows-based examination of the Bluetooth identity and cached device record. The project determined that:

```
Windows registry name
        ≠
actual Bluetooth broadcast name
```

This proved that the system’s real identity is not controlled by the host OS. Instead, the firmware within the module or its EEPROM/configuration memory defines the broadcast name. This has several major implications:

1. Device identity is part of the embedded firmware configuration.
2. The underlying SoC must have a way to store system settings.
3. The Bluetooth name and MAC address may be stored in persistent memory or in a firmware-defined region.
4. A full technical understanding of the board requires direct investigation of the embedded system itself, not just the Windows device stack.

These conclusions are central to the scientific basis of the project.

## 10. Controlled Experimentation Philosophy

The project explicitly rejects a purely superficial approach. The objective is not to simply change the Bluetooth name from `CHARGE MINI` to something else. Instead, the module is treated as a complete embedded system where configuration values, firmware state, and hardware interfaces must be understood before any modification is attempted.

The name change experiment is therefore positioned as a secondary validation step, not as the principal research objective.

This approach aligns with sound reverse-engineering practice:

- understand the system first,
- verify the root cause of behavior,
- confirm the relevant storage/interface paths,
- then attempt controlled modification.
